# Maple Court synthetic demo policy pack

This bundle is fictional project data for an explicitly isolated demonstration. It is not approved production policy, legal guidance, a licensing record, a real vendor roster or an emergency operating procedure. Every normalized source remains `temporary_fixture` with `production_eligible: false`. Do not convert these values to active/approved to pass a demo.

## Provenance and corrections

The user supplied five policies and 12 evaluation cases in the `tento-demo-policy-pack` folder. The Markdown body of each policy is copied verbatim after a new machine-readable metadata header; the original warnings, blank display Status fields and wording are retained. The header's explicit synthetic status governs this normalized data. Manifest hashes record both the normalized source bytes and original body bytes. The original Downloads folder is unchanged.

The supplied manifest repeated `MC-OPS` as the identifier for four different policies. The normalized manifest uses full unique IDs `MC-OPS-001`, `MC-SAFE-002`, `MC-OPS-003`, `MC-OPS-004`, and `MC-OPS-005`, matching the original policy titles and evaluation references. Its varying test status strings are normalized to the repository's `temporary_fixture` vocabulary. Authority `internal_sop` is a fictional corpus classification, not real approval; `US-VA` is only a routing label and establishes no legal rule. Dates remain fictional test dates.

`claims.json` contains ten exact contiguous body passages with Unicode character offsets measured against each full normalized Markdown string. `outcome` intentionally preserves the exact selected passage instead of inventing permissions. Several supplied citation-anchor bullets paraphrase body text, so no anchor list is used as the authority for a canonical claim. The in-house passage retains its training, authorization and safety conditions; specialist scope retains the prohibition on inferred credentials.

`cases.json` preserves the twelve original queries and expected behavior, then adds three clearly marked project-generated synthetic routine cabinet, nonsecurity door-hardware and filter-maintenance cases. Expected source IDs are separate from answer authorization: a policy can be retrieved while an unsupported legal, billing, safety-certification or completion request must still abstain. This is a development set, not held-out evidence for production accuracy.

## Runtime boundaries

Use a dedicated demo source loader or isolated demo tenant. Existing production-source ingestion must continue rejecting this bundle. Models may propose demo assessments; deterministic safety, PII, scope, citation and schema controls still apply. The policy pack's P1 labels do not downgrade the application's deterministic P0 emergency verdict. Human-review phrases inside the copied source describe its fictional operations; they do not create an annotation queue or grant tools.

No document authorizes sending notifications, contacting emergency services, licensing a vendor, collecting charges, altering a lease or reporting a real completed repair. A saved internal demo work-order record is distinct from an actual scheduled or completed visit.
