RESIDENT OS — REQUIREMENT REGISTER AND ACCEPTANCE MAP
======================================================

Document status: Draft baseline for Phase 0 (contract freeze)
Last updated: 2026-09-09
Companion document: ../req.txt

USAGE
-----
This is the testable register for the whole project. Requirement IDs are stable.
Use them in issue titles, pull requests, test names, evaluation reports, and
release evidence. Do not mark an item complete because code exists: record a
test, evaluation run, or operational rehearsal as its evidence.

STATUS KEY
----------
Not started = no accepted implementation evidence.
Planned     = scheduled for the stated delivery phase.
Verified    = acceptance evidence is linked below.
Blocked     = cannot progress without a named external decision or dependency.

ALL CURRENT REQUIREMENTS ARE NOT STARTED UNLESS EVIDENCE IS ADDED.

REQUIRED PHASE-0 CONTRACTS
--------------------------
The following are mandatory before feature implementation. Each must be accepted
together because a partial contract freeze creates incompatible assumptions.

1. Domain vocabulary for priority, ticket status, trade, responsible party,
   authority, guardrail, rejection reason, decision mode, notification tier,
   role, and failure kind.
2. OpenAPI contract for tickets, runs, decisions, approvals, errors, pagination,
   authentication, and idempotency.
3. SSE event contract for step lifecycle, retrieval, guardrail, council,
   decision, and failure events.
4. Initial schema: property domain, AI/audit spine, knowledge, evaluation, tenant
   RLS, append-only protections, and migrations.
5. Typed cross-agent contracts: TicketFacts, ContextEnvelope, Claim, Diagnosis,
   DispatchPlan, AuditResult, Decision, SafetyVerdict, and JudgeScores.
6. Threat model: cross-tenant access, prompt injection, PII, tool authority,
   vendor links, audit integrity, provider failure, and notification misuse.
7. Test plan mapping every ID in this file to unit, integration, evaluation,
   adversarial, and release evidence.

TRACEABILITY RULES
------------------
- Code, tests, migrations, prompts, and dashboards must reference the applicable
  requirement ID(s) in their issue or pull-request description.
- Each requirement marked Verified must list durable evidence: a test path and
  command, evaluation report path/run ID, or operational rehearsal date.
- A requirement change updates ../req.txt and this file in the same change.
- New requirements receive the next ID within their family (FR, SR, or QR) and
  include a phase and acceptance criterion before implementation begins.
- Metrics remain targets until the linked evidence proves the result.
