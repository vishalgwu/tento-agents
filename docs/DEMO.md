# DEMO.md

**How to demo Resident OS, what has to be real, and what to check before anyone sees it.**
Owner: both tracks · Last updated: 2026-07-25
**Related:** `PRD.md` §9 (release criteria) · `DESIGN.md` (surfaces) · `PHASES.md` (Phase 5 is the demo-ready gate)

> The demo is a deliverable with its own definition of done, not a thing you improvise on the day. Phase 5 is not complete until every checklist in §3 passes on the production URL.

---

## 1. What the demo has to prove

Different audiences need different things proven. The click path is mostly the same; the narration is not.

| Audience | What they're deciding | The one moment that decides it |
|---|---|---|
| **Recruiter / hiring manager** | Is this person worth an interview | The eval report with a red number on it |
| **Technical interviewer** | Do they understand what they built | Council disagreement + the abstention card |
| **Investor** | Is there a company here | The compliance flip and the governance strip |
| **Operator / builder** | Would this save me money | The queue, with zero AI vocabulary |

Everything below is built around those four moments.

## 3. Pre-flight checklist

Run this before every public link, every recorded demo, and every interview.

### 3.1 Hard blockers — do not demo if any fails

- [ ] `DEMO_MODE=true` in production env, verified by triggering a notification and confirming zero outbound delivery
- [ ] No real phone number, email, or address exists anywhere in seeded data
- [ ] Supabase is on Pro (the free tier pauses after 7 idle days — a paused database mid-demo is unrecoverable)
- [ ] All five demo tickets resolve to their expected outcomes on a fresh run
- [ ] The eval report at `/evals` matches the committed `docs/evals/REPORT.md` and both cite the same git SHA
- [ ] Red-team fair-housing suite is green in the latest CI run
- [ ] No placeholder or hardcoded number appears on any dashboard

### 3.2 Soft checks

- [ ] p95 decision latency under 20s measured in the last hour (cold Fly machines add several seconds — hit the URL once, five minutes before)
- [ ] Model provider status pages clear
- [ ] Backup demo video accessible offline
- [ ] Both light and dark themes render correctly on the machine you're presenting from
- [ ] Browser zoom at 100%, notifications silenced, only the demo tab open

### 3.3 Reset

```bash
make demo-reset    # truncates runs/decisions/tickets, re-seeds, re-embeds KB, warms caches
```

Run it before every session. A queue with yesterday's approvals already actioned is a flat demo.

## 4. The 2-minute recruiter demo

The default. Assume they will not click anything themselves and will leave after 30 seconds if nothing happens.

| Time | Screen | Action | What you say |
|---|---|---|---|
| 0:00 | README | — | *Nothing.* Let the streaming-trace GIF play. Silence here is correct. |
| 0:10 | Landing | Click **Resident** | "This is a resident at 11:40pm with a leak." |
| 0:15 | Resident submit | Click prompt 1, submit | "Acknowledged instantly — that never waits on a model. The reasoning runs behind it." |
| 0:30 | Resident ticket #4471 | Expand "Why?" | "It's telling her *why* she isn't being charged, and naming the lease clause." |
| 0:45 | Landing → **Manager** | Open queue | "Sorted by deadline risk, not arrival time." |
| 0:55 | Queue | Point at card 3 (#4463) | "Look at the third one. Confidence 0.44 — it declined to decide and said exactly what it was missing." |
| 1:10 | Trace on #4471 | Open trace | "Every step, prompt hash, cached tokens, cost. Three of these have no model call at all." |
| 1:25 | Council on #4468 | Open council view | "Three specialists with deliberately different evidence. They disagreed, and the disagreement was the useful part." |
| 1:35 | Resident → prompt 5 | Submit voucher question | "Now watch what happens here." |
| 1:45 | Guardrail block | Show block + CI job | "It refuses, logs it, routes to a human. And that's the CI job running protected-class probes on every commit." |
| 1:55 | `/evals` | — | "Every number, including the one I missed." |

**Stop at 2:00.** Do not keep going. If they're interested they will ask, and answering a question is worth more than the next screen you would have shown.

## 5. The 5-minute technical interview demo

Same path, different emphasis, and you talk about constraints rather than features.

**Open with the constraint, not the product:**
> "Reliability compounds — ten LLM steps at 95% each is 60% end to end. So I budgeted five model calls on the critical path and made everything else deterministic. Three in the normal path, five when council fires."

Then:

1. **Trace viewer (90s).** Walk the span tree. Point out `context.broker`, `context.budget`, and `decision.gate` are code, not model calls. Show the citation verification block: "that's deterministic — I don't need a judge to tell me a citation doesn't resolve."
2. **Retrieval inspector (60s).** BM25 list, vector list, RRF merge, rerank delta, the token-budget cut line. "Embeddings smear identifiers — `SOP-PLM-04` ranked 47th in dense-only. Hybrid took recall@5 from 0.62 to 0.84."
3. **Council (90s).** The "blind to" line under each member. "Three samples of the same model over the same context aren't independent — they agree confidently and wrongly. Splitting the evidence makes disagreement informative." Then: "and I measure whether it earns its place. Lift is +0.043 on priority F1. If it were flat, I'd delete it."
4. **Eval dashboard (60s).** Calibration curve, tolerance bands, pinned judge. "The judge is a regression detector, not ground truth — published agreement with human raters is 85 to 92%. The labelled set is the anchor."
5. **Degradation (30s).** "Let me kill the API key in staging." Show rules-only mode. "The building keeps running when a provider doesn't."

**Have ready when they push back:** why not CrewAI, why Postgres over a vector DB, why you didn't buy a memory vendor, how injection is handled architecturally rather than by scanning, and what the weakest part is. That last answer matters most — see `04-execution-and-career.md` §5 Q12.

## 6. The 3-minute investor demo

No architecture. Numbers, then the wedge.

1. **Problem, 30s.** "3.3 maintenance requests per unit per year, about $200 each. Triage is a human guessing at urgency, trade, and who pays. Wrong one way is a $150 truck roll; wrong the other way is a habitability statute."
2. **Product, 60s.** Queue → one decision → its citations. "Every decision comes with its receipts."
3. **The wedge, 45s.** The compliance flip. "HUD put AI inside the Fair Housing Act in 2024. Testing organisations can probe a live leasing bot remotely, at scale, in an afternoon. Every vendor says they're compliant — what they mean is a line in a system prompt. This is a CI job with protected-class probes."
4. **Governance strip, 30s.** Owner dashboard. "412 decisions, complete evidence chain on every one, exportable. Nobody else ships this."
5. **Economics, 15s.** "Inference is about $73 per property per year against a $12,000 account. Margin isn't the constraint here — distribution is."

**Expect and answer honestly:** *"What's your moat?"* → "Right now, nothing durable. The compounding assets are the labelled decision corpus and the jurisdiction-mapped guardrail library, and neither exists until there are customers." Naming your non-moats reads as credible; claiming five reads as naive.

## 7. The operator / builder demo

**Rule: do not say "agent," "LLM," "RAG," "council," or "confidence score."** Not once.

1. Manager queue. "Eleven decisions waiting, ordered by what's closest to breaching."
2. One card. "Third drain call in fourteen months. It caught the pattern and recommended replacing the trap instead of snaking it again — that's the difference between a $90 repeat visit and fixing it."
3. Approve. "Five seconds."
4. Card 3. "This one it wasn't sure about, so it asked you. That's deliberate."
5. Owner dashboard. "Cost per unit, SLA compliance, and the units that keep failing — with what you've spent on each."
6. Vendor link. "No app to install. Two taps."

Then stop and ask: *"What's the part of your day this doesn't touch?"* The answer is worth more than the rest of the demo.

## 8. The compliance flip, in detail

The most important fifteen seconds, and the easiest to get wrong.

**What must happen:** the system produces **no answer**. It shows a guardrail block naming `fair_housing`, writes a `guardrail_events` row, routes to a human queue, and the resident sees a neutral "a team member will follow up shortly."

**What must never happen:** a generated response that discusses source of income, even a careful one. If your system produces a well-worded reply here, the guardrail failed and you should not demo it until it doesn't.

**Show alongside it:** the CI run of `evals/datasets/redteam_fh.jsonl` — paired probes identical except for a protected-class signal, asserting response parity on latency class, information completeness, and tone.

**Say:** "This is exactly the test a fair-housing testing organisation would run against a live bot. I run it against myself on every commit."

**Do not** turn this into a lecture on housing law. Fifteen seconds, then move.

## 9. Real vs seeded

State this on the landing page. Rigour reads as rigour; hiding it reads as fabrication when someone notices.

| Element | Status | Note |
|---|---|---|
| Agent runs, traces, prompt hashes, token counts, costs | **Real** | Live execution against real model APIs |
| Retrieval scores, RRF ranks, rerank deltas | **Real** | Computed at query time |
| Eval metrics, calibration curve, council lift | **Real** | From a committed run with a git SHA |
| Guardrail verdicts | **Real** | Live |
| Abstention on #4463 | **Real** | Genuine threshold behaviour, not a hardcoded card |
| Property, units, residents, tenancies | Seeded synthetic | Generated, no real people |
| 1,200 historical tickets, vendor scorecards | Seeded synthetic | Realistic distributions |
| Owner dashboard month-over-month figures | Seeded synthetic | Derived from seeded history |

**Landing page line:** *"Synthetic property — 412 units, 1,200 historical tickets. All AI execution, retrieval, and evaluation is live."*

**If you fake one thing, fake nothing.** The abstention card is the best moment in the demo precisely because it's real behaviour; hardcoding it would make every other claim suspect the moment someone probed it.

## 10. When it breaks live

It will, eventually. Recovery is part of the demo, and handling it well is a better signal than a clean run.

| Failure | Say this | Then |
|---|---|---|
| Provider slow or down | "This is the degradation path — it drops to rules-only and everything routes to review." | Show it. This is a *better* demo moment than the happy path. |
| Cold start delay | "Fly machines scale to zero. First request wakes them." | Keep talking; don't refresh. |
| Decision differs from expected | "Non-deterministic — let me show you the trace and we can see why." | Open the trace. Never pretend it went as planned. |
| Total outage | "Let me show you the recording, and we can walk the code instead." | Backup video, then the repo. |

**Never apologise repeatedly, never blame the network, never say "it usually works."** Show the failure path you designed for. That is the point of having designed one.

## 11. Demo mode specification

`DEMO_MODE=true` must:

- Block every outbound channel — push, email, SMS, voice — at the transport layer, not by config the app reads. A notification renders in the UI and is written to `notifications` with `status='demo_suppressed'`.
- Pin temperature and seeds so runs are reproducible across sessions.
- Disable all destructive admin endpoints.
- Show a persistent, non-dismissible strip: *"Demo environment — synthetic data, no messages are sent."*
- Log every run with `demo=true` so demo traffic never pollutes eval or metrics baselines.

CI asserts that with `DEMO_MODE=true`, no transport adapter is reachable. This is a test, not a convention.

## 12. Recordings

Two artifacts, both produced in Phase 9.

**README GIF — 90 seconds, silent, looping, under 8MB.** Submit → stream → decision with citations → approve → the diamond changing from machine to human. No cursor wandering, no dead air. This is what 80% of visitors will see and the only thing many of them will see.

**Loom — 3 minutes, narrated.** The 2-minute script plus 60 seconds of architecture at the end. Linked from the README, from every application, and from LinkedIn.

**Do not** record a 20-minute walkthrough. Nobody watches it, and its existence signals you don't know what matters.

---

## 13. Anti-patterns

- Making them sign up, fill a form, or read before they can see anything
- Narrating the architecture during the recruiter demo — show the product, save architecture for when they ask
- Autoplaying audio
- Opening with the trace viewer (it's the payoff, not the hook)
- Demoing on a machine with notifications on
- Saying "this is just a prototype" — the eval report is the appropriate caveat and it's a stronger one
- Claiming a customer, a pilot, or an outcome that doesn't exist
- Going past your time budget because it seems to be going well
